# ADR-017: a restore is not a manifest — the deps gate repairs the compile and leaves the load broken

Status: Accepted (2026-09-04)

Supersedes nothing. Extends ADR-008 (*mtime is never a content oracle*) with the
rule that decides when mtime is nevertheless the RIGHT comparison, and closes one
false-fresh hole ADR-008's suppression opened.

## Context

Two artefacts are derived from a project's restore, by two different commands:

| artefact | written by | read by |
|---|---|---|
| `obj/project.assets.json` | `dotnet restore` | the compiler, for `-r:` |
| `bin/<tfm>/<Asm>.deps.json` | `dotnet build` (`GenerateBuildDependencyFile`) | the **host**, to resolve assemblies at run time |

`DepsFreshness` detects a stale restore and repairs it by shelling `dotnet
restore`. That repairs the FIRST row and cannot touch the second. So a workspace
whose restore was superseded ends up with a correct compile and a manifest listing
the reference closure of a restore that no longer exists.

The consequence is asymmetric and that is what makes it expensive:

- at compile time the truncated closure is `FS0074: the type referenced through 'X'
  is defined in an assembly that is not referenced` — and the automatic restore
  repairs it, so the next build succeeds and the error reads as transient;
- at run time the host resolves through the manifest, not through the directory. An
  assembly sitting in the output folder and missing from the manifest is
  `FileNotFoundException: Could not load file or assembly`, on exactly the routes
  that touch it. A green build and a red run, on specific routes only —
  indistinguishable from an application bug.

Observed three times in one day in three reused `jj` workspaces (AUTOMATION-528),
each costing hours, each time passing in a fresh workspace of the identical tree.

Reproduced against a real SDK before this ADR was written: a two-project tree built
green, then the manifest an earlier build had genuinely written restored over it.
`Lib.dll` in the output folder, every assembly newer than every source, every copy
byte-identical to its origin, `grep -c '"Lib'` = 0 in the manifest against a
non-zero positive control for the directly-referenced project — and
`Could not load file or assembly 'Lib'` on the run.

## Decision

### 1. `ArtifactFreshness` gains a fourth stale case, and it is an mtime judgement

`DepsManifestOlderThanRestore`: the run target's `bin/<tfm>/<Asm>.deps.json` is
older than its `obj/project.assets.json`.

ADR-008's rule is "content by default; if you reach for mtime, use it only as a fast
path and name the content-aware backstop." This case reaches for mtime and names no
backstop, and that is correct, on the same grounds as `verifyArtifactsFresh`:

**mtime is the right comparison exactly when the two files share no bytes and the
question is temporal.** A `.fs` and the `.dll` compiled from it share no bytes; a
restore and the manifest generated from it share no bytes. There is no "expected
manifest content" to hash against, so a content check is not merely more expensive
here — it is not expressible. Whereas a build-output COPY *is* its origin's bytes,
which is why `OutputCopyFreshness` is content-only and must stay that way.

So the two defaults the ticket asks about are not in conflict and neither is wrong:
they answer different questions. The rule that decides between them is *do the two
files share bytes?*, not *which subsystem is this?*.

Guard rails:

- **Strict `>`.** A build writes the restore first and the manifest after it, so
  equal timestamps — a coarse filesystem, or both inside one tick — are the normal
  healthy shape and must not read as stale.
- **Absence is never staleness.** Either half missing means there is nothing to
  compare: a project with no `obj/` and a library that generates no manifest are
  both legitimate.
- **Asked of the run target only, never of its closure.** The host resolves through
  the entry assembly's manifest; a library's own `deps.json` is never read. Asking it
  of the closure would manufacture refusals nothing can act on.

### 2. It REFUSES, and it is not healed

`StaleArtifactPreflight` heals exactly one case, `CopyDiffersFromOrigin`, because
the repair is a byte copy whose source is on disk. This one is generated by an
MSBuild target; nothing on disk holds the bytes it would produce, and writing a
plausible one would put the preflight in the business of inventing a reference
closure. It refuses, names both files, and names `dotnet build`.

The refusal also names the WRONG fix, because it is the one a reader reaches for
first: adding a direct `ProjectReference` to whatever failed to load puts an entry
in the manifest and makes the symptom vanish while the superseded restore stays
exactly where it was. That is a fix that works for the wrong reason and it hides the
defect. The remedy text says so, and says that a `dotnet restore` will not help
either — which is the non-obvious half, since the message is about dependencies.

### 3. A matching content baseline may never certify a MISSING restore

ADR-008 added `MatchesFreshBaseline`: a `Stale` mtime verdict whose dep-relevant
signature is unchanged is proceeded on, because a compile-item-only fsproj edit
bumps the mtime without touching the package graph.

`Stale` is two facts wearing one label — *the assets are older than a dep file*, and
*there are no assets at all* — and the baseline can only vouch for the first.
Nothing in `depRelevantSignature` is derived from `obj/`, so an ordinary
`rm -rf obj/` leaves the signature exactly where it was and the suppression arm
would certify a project with no restore output on disk at all. FCS would then
type-check against an empty reference set and produce the phantom
"namespace/type not found" storm the gate exists to prevent.

`evaluateProject` already receives the `assetsPresent` probe. The suppression arm
now requires it.

## What was falsified

AUTOMATION-538 reported the mirror failure — a content-identical touch of
`Directory.Build.props` wedging the gate with no way out — and attributed it to
`dotnet restore` "exiting with a hard failure" because it "refuses to rewrite an
assets file it considers already up to date".

Measured: the trigger reproduces, the wedge does not. A content-identical rewrite
moves the mtime (byte-identical SHA-256, `project.assets.json` now older), so
`compareFreshness` does report `Stale`. But `dotnet restore` then prints
`All projects are up-to-date for restore` and **exits 0**, leaving the assets
untouched — and per `evaluateProject` a no-op success with assets present is
`RecoveredOk`, which proceeds and clears the diagnostic. `FailFast` requires restore
to genuinely exit non-zero or to exceed `restoreStepTimeout`.

So the false-STALE verdict is real and its documented consequence is not. What
remains of it is a COST, not a wedge: one spurious restore chain per project on the
first sighting after such a touch (`dotnet restore`, plus a `paket restore` per lock
group, plus `tool restore`), which under contention can reach the 5-minute per-step
timeout and only then produce the red 538 describes. That is worth fixing, but it is
a latency problem with a different shape, and building a durable on-disk baseline for
it was deliberately NOT done here — see below.

## Deliberately not done

**A durable, cross-process fresh-signature baseline.** 538's own suggested shape,
and it would remove the spurious restore. Rejected for now for a reason that only
appears when both directions are held at once: that spurious restore is currently
LOAD-BEARING for the compile half of direction A. Merging into a long-lived
workspace bumps the fsproj mtime via compile items, the probe reads `Stale`, no
baseline exists in a fresh process, and the restore that fires is what repairs the
truncated closure by accident. Persisting the baseline would suppress exactly that
restore and make the `FS0074` half worse while fixing a latency problem.

The precondition is the finding below. Once the signature covers everything that can
change a project's restore graph, the baseline can be made durable safely.

## Follow-up finding: the dep signature is blind to the `ProjectReference` closure

`depRelevantSignature` and `dependencyFiles` span the project's OWN `.fsproj` plus
its ancestor dep files. A project's restored closure also depends on the `.fsproj`
of every project it references, transitively: when project B gains a
`ProjectReference`, project A's `project.assets.json` is stale and NEITHER A's mtime
probe NOR its content signature can see it. That is the root of direction A's
truncated closure, and the reason the current code only ever recovers from it by
accident.

Fixing it is a strictly larger change than this one (a `ProjectReference` resolver
in core, with property expansion, matching the one `ArtifactFreshness` already has
in `FsHotWatch.TestPrune`), and AUTOMATION-528's approval comment explicitly scoped
this work to detection. Recorded here so it is not re-derived: it is the precondition
for the durable baseline above.

## Consequences

- A superseded restore is now REPORTED before any suite launches, naming both files
  and the command that fixes it — instead of surfacing later as a
  `FileNotFoundException` inside a test whose name has nothing to do with it.
- One new refusal class that a plain `dotnet build` always clears. It cannot fire on
  a tree that has been built since its last restore, because a build writes the
  manifest after the restore it reads.
- The rule for future freshness work: **content by default (ADR-008); mtime exactly
  when the two files share no bytes.** Say which, and say why, at the site.
