## Summary

Three follow-ups from the original 8-item survey at the bottom of
`docs/plans/2026-04-30-framework-tightening-design.md`:

- **Item 5 (broad `try/with _` swallows)** — the survey is right. The
  `BuildInputsHasher` mtime swallow at `src/FsHotWatch.Build/BuildPlugin.fs:112`
  is the most insidious of the three: a transient `IOException` quietly
  collapses every same-path entry into a single bogus `(path, 0L)` cache key
  and freezes the build merkle. Highest priority fix. The TestPrune log/CTRF
  swallows are fine in spirit but should narrow to IO exceptions; the Daemon
  subtask snapshot swallow is dead defense and should be deleted.
- **Item 6 (path normalization through typed wrappers)** — the survey is
  partly right. The typed wrappers exist (`Events.fs:9, 17`) and the project
  graph is already typed end-to-end. The leak is at the `FileCheckResult.File:
  string` boundary (`Events.fs:65`), which forces every plugin that consumes
  `FileChecked` to either trust an opaque "FCS normalizes for us" assumption
  (Lint, Analyzers) or re-normalize on every event (BuildPlugin's
  `WaitingForFcsPhase` drain). Migration is concretely scoped — about a dozen
  call sites — but touches every plugin, so it lands as one larger commit.
- **Item 8 (TestPrune duplicate `QueryAffectedTests`)** — the survey is right
  about the duplication but wrong about which call to drop. The per-FileChecked
  query at `TestPrunePlugin.fs:1085` is the one with a real consumer (the
  `affected-tests` IPC command at `:827`). The CHANGELOG even documents why
  it was added. The cleanest cut is to keep the symbol-set in state and let
  the IPC handler compute on demand — but that change should land **after
  Phase 3** (TestPrune RunExclusive migration), not before, because Phase 3
  rewrites the surrounding `Update` handler.

## Item 5 — Broad `try/with _` swallows

### Site A — `BuildInputsHasher.hashFile` mtime read

**Current code** (`src/FsHotWatch.Build/BuildPlugin.fs:110–124`):

```fsharp
let hashFile (path: string) =
    let mtime =
        try
            File.GetLastWriteTimeUtc(path).Ticks
        with _ ->
            0L

    cache.GetOrAdd(
        (path, mtime),
        fun _ ->
            try
                FsHotWatch.CheckCache.sha256Hex (File.ReadAllText path)
            with _ ->
                "read-error"
    )
```

**What's actually possible.** `File.GetLastWriteTimeUtc` on .NET can throw:
`UnauthorizedAccessException`, `PathTooLongException`, `IOException` (file
locked), `FileNotFoundException` is not thrown — it returns
`1601-01-01T00:00:00Z` for non-existent files. So `0L` is a sentinel that
*could* mean "I/O error" (rare), but never "file missing" (which has its own
representable mtime).

**What it hides.** The whole point of `BuildInputsHasher` (per the comment at
`:102`) is "amortized O(changed) cost" — its cache is keyed on
`(path, mtimeTicks)`. If `GetLastWriteTimeUtc` throws transiently for one
call and succeeds for the next, the same physical file produces two distinct
cache keys: `(path, 0L)` and `(path, realMtime)`. The first hits the inner
`File.ReadAllText`, which itself is wrapped in `try/with _ -> "read-error"`
— so the cache may permanently store `(path, 0L) -> "read-error"`. Subsequent
inputs-merkle computes that include this file under contention can keep
returning `"read-error"`, which folds into the merkle and produces a stable-
looking but *poisoned* build cache key. The §2a build cache will happily
replay the poisoned entry on the next build.

Concrete failure mode: under FSEvent storms or jj operations holding file
handles, the mtime read fails for one file. The merkle gets `"read-error"`
folded in. The §2a cache then claims any future build with the same set of
*other* files is up to date — even if the locked file's content changed.
Silent under-build.

**Replacement.** Two changes, both narrow:

```fsharp
let hashFile (path: string) =
    if not (File.Exists path) then
        // Honest "missing" sentinel that the merkle can detect and refuse.
        None
    else
        let mtime = File.GetLastWriteTimeUtc(path).Ticks  // let real exns propagate
        Some (
            cache.GetOrAdd(
                (path, mtime),
                fun _ -> FsHotWatch.CheckCache.sha256Hex (File.ReadAllText path)))
```

`Compute()` becomes:

```fsharp
let perPath =
    allInputs
    |> List.map (fun p ->
        match hashFile p with
        | Some h -> p, h
        | None -> p, "missing")  // distinct from any real hash
```

`IOException` and friends now propagate up to `decideBuildOutcome`, which
already turns failures into a real `BuildOutcome.BuildOutputFailed` — so the
build is honestly marked failed instead of silently re-using a stale cache
entry.

**Risk:** Low. The behavior change is "transient IO errors now fail loudly
instead of poisoning the cache." Under normal operation the path always
exists.

**Cost:** Low. ~15 lines.

### Site B — TestPrune log persistence + CTRF flakiness recording

**Current code** (`src/FsHotWatch.TestPrune/TestPrunePlugin.fs:472–480`):

```fsharp
try
    let logDir = testRunsDir repoRoot
    Directory.CreateDirectory(logDir) |> ignore
    ...
    File.WriteAllText(logPath, output)
    Logging.info ...
with ex ->
    Logging.error "test-prune" $"Failed to persist test output: %s{ex.Message}"
```

And `:525–533` (CTRF flakiness):

```fsharp
try
    let records = Flakiness.parseCtrfTests (File.ReadAllText p)
    ...
    File.Delete p
with ex ->
    Logging.warn "test-prune" $"flakiness: failed to record run: {ex.Message}"
```

**What's possible / what it hides.** Both genuinely *want* "best-effort —
don't fail the test run because we couldn't write a log." But `with ex ->`
also swallows programming bugs (e.g. a future `Flakiness.parseCtrfTests`
refactor throws `ArgumentNullException` for an empty CTRF) — they show up as
a single warn line and a silently broken flakiness DB.

**Replacement.** Narrow to expected exceptions:

```fsharp
with
| :? IOException as ex
| :? UnauthorizedAccessException as ex ->
    Logging.error "test-prune" $"Failed to persist test output: %s{ex.Message}"
```

For the CTRF parse case, also catch `JsonException` (parse failures from a
runner emitting malformed JSON) but let `NullReferenceException` /
`InvalidOperationException` propagate.

**Risk:** Low. The narrowing is purely additive on the diagnostics side.

**Cost:** Low. ~10 lines, two sites.

### Site C — Daemon subtask snapshot

**Current code** (`src/FsHotWatch/Daemon.fs:629–632`):

```fsharp
let subtasks =
    try
        host.GetActivitySnapshot(name).Subtasks
        |> List.map (fun t -> t.Key, t.StartedAt)
    with _ ->
        []
```

**What's possible.** `GetActivitySnapshot` is defined at
`src/FsHotWatch/PluginActivity.fs:299–321`. It locks `pluginsGate` for a
`TryGetValue`, returns an empty record if missing, otherwise locks the
plugin's own `Gate` and reads. There is no path that throws under normal
operation — the function is fully defended.

**What it hides.** Programming bugs only. If a future refactor introduces a
`KeyNotFoundException` or null deref inside `GetSnapshot`, this `with _`
swallows it and the wait-loop's "Waiting for plugins: …" diagnostic silently
stops listing subtasks. Hard to debug.

**Replacement.** Delete the `try/with`. `GetActivitySnapshot` already returns
`{ Subtasks = []; ... }` for unknown plugins; that's the correct fallback. If
a real exception ever occurs, it propagates to the wait-loop's existing
async-block error handling.

**Risk:** Very low. The empty-list fallback is preserved by
`GetActivitySnapshot`'s contract.

**Cost:** Trivial. ~4 lines deleted.

## Item 6 — Path normalization through typed wrappers

### Current state of typed paths

`src/FsHotWatch/Events.fs:9, 17` defines `AbsFilePath` and `AbsProjectPath`
as `private` single-case DUs whose `create` runs `Path.GetFullPath`. The
project graph (`src/FsHotWatch/ProjectGraph.fs:90, 101, 112`) is fully typed:
`GetAllProjects: unit -> AbsProjectPath list`, `GetAllFiles`,
`GetProjectsForFile(AbsFilePath)`, etc.

The leak is `FileCheckResult.File: string` (`Events.fs:65`). FCS produces a
`string` and the record currently echoes it. Every downstream consumer
re-derives normalization in different ways:

### Map of every normalization site

| Site | What it does | Why |
|---|---|---|
| `CheckPipeline.fs:92` (`InvalidateFile`) | `Path.GetFullPath` on incoming path | match keys in `projectOptionsByFile` (which is loaded with full paths) |
| `CheckPipeline.fs:261, 288` (`CheckFile`, `CheckFileWithOptions`) | same | same |
| `Daemon.fs:218` (FCS option scan) | `Path.GetFullPath(fcsOptions.ProjectFileName)` | normalize FCS-yielded project string before comparing |
| `Daemon.fs:496` | `allSourceFiles |> List.map AbsFilePath.create` | already typed at this site |
| `BuildPlugin.fs:168` (`normalizePath`) | `Path.GetFullPath` on every file path | drain `WaitingForFcsPhase: Set<string>` populated by SourceChanged events vs. consumed against `result.File` |
| `BuildPlugin.fs:171` | `AbsFilePath.create` for `GetProjectsForFile` | ad-hoc |
| `BuildPlugin.fs:331` | `List.map AbsFilePath.create` for `GetAffectedProjects` | ad-hoc |
| `TestPrunePlugin.fs:984` | `Path.GetRelativePath(repoRoot, result.File).Replace('\\', '/')` | derive cross-platform relpath key for SymbolSnapshot map |
| `Lint`, `Analyzers` | use `result.File` directly as `Map<string, _>` key | trust FCS normalization |

Two clusters emerge:

1. **"Match against an internal index keyed by absolute path"** —
   `CheckPipeline.InvalidateFile`, `CheckFile`, `BuildPlugin.WaitingForFcsPhase`.
   These exist *because* `FileCheckResult.File` is untyped: a caller of
   `CheckFile("rel/path.fs")` would today produce a different key than the
   FCS-emitted one.
2. **"Compute relpath / project lookup"** — TestPrune, BuildPlugin's
   `isTestFile`. Once a path is `AbsFilePath`, both reduce to one-liners.

### Why `FileCheckResult.File` stayed `string`

Two reasons, in order of weight:

1. The record is constructed inside `CheckPipeline.CheckFileCached` from FCS
   values where the immediate input is a `string`. Wrapping it in
   `AbsFilePath` was easy to defer when the type was originally introduced.
2. Public API: `FileCheckResult` is exported. Changing `File: string` →
   `File: AbsFilePath` is a public type-change. Per CLAUDE.md the version
   bumper handles this; the framework is pre-1.0 so it's acceptable. But it
   *is* a real downstream-breaking change for anyone consuming the
   `FsHotWatch` library outside this repo.

### Proposed change

Make `FileCheckResult.File: AbsFilePath`. The boundary normalization happens
once, in `CheckPipeline.CheckFileCached`, where the FCS string becomes an
`AbsFilePath`.

```fsharp
// Events.fs
type FileCheckResult =
    { File: AbsFilePath
      Source: string
      ...
    }
```

Then plugins drop normalization:

- **CheckPipeline:** internal indexes (`projectOptionsByFile`, `fileTokens`,
  `fileLocks`) become `Dictionary<AbsFilePath, _>`. `InvalidateFile`, both
  `CheckFile` overloads accept `AbsFilePath`. The `Path.GetFullPath` calls
  at `:92, 261, 288` go away.
- **BuildPlugin:** `normalizePath` deleted. `WaitingForFcsPhase: Set<AbsFilePath>`.
  `isTestFile: AbsFilePath -> bool`. Lines 168, 427, 547, 567 collapse.
- **TestPrunePlugin:** add a small helper at the boundary
  `relPathFor (repoRoot: string) (file: AbsFilePath): string`. Use it once
  inside the `FileChecked` handler; rest of the code stays.
- **Lint, Analyzers:** their `Map<string, _>` becomes `Map<AbsFilePath, _>`.
  Reference-equality of strings was never load-bearing; semantic equality of
  the wrapped path is identical.
- **`EmitFileChanged`** stays as-is (`SourceChanged of files: string list`).
  The watcher emits raw paths from FSEvents; normalizing at the watcher
  boundary is a separate change. **Out of scope here** — flagging only.

### Migration cost

Concretely (counted from the grep results above):

- 5 plugin signature touches (Lint, Analyzers, BuildPlugin, TestPrune,
  FileCommand — last two are wildcard match, no signature change).
- 6 internal CheckPipeline edits.
- 1 Events.fs edit.
- ~12 test files reference `result.File` (sampled — actual count likely
  similar). Each becomes `AbsFilePath.value result.File` at the assertion
  boundary, or migrates fully.
- Public API change: documented in CHANGELOG; semver bumper picks it up.

### Risk

Medium. The change is mechanical but touches every plugin's signature.
Compiler catches all sites. The risk is missing a string-key-into-map case
in tests where the test's literal path string accidentally matched FCS's
normalization on macOS/Linux but not Windows; today this works because
everyone re-normalizes. Mitigation: run `mise run test` and the integration
suite both locally and on CI before merge.

### TDD strategy

- Add one unit test demonstrating the BuildPlugin `WaitingForFcsPhase` drain
  works without `normalizePath`: emit `SourceChanged ["./relative.fs"]`,
  emit a `FileChecked` whose `result.File` was constructed from
  `AbsFilePath.create "/abs/relative.fs"`. Assert the plugin drains the
  awaiting set. (Today this only works because both sides normalize; after
  the migration, both sides carry `AbsFilePath` whose normalization
  happens inside the constructor.)
- Existing daemon + plugin tests catch behavioral regressions; the
  type-system catches signature mismatches.

## Item 8 — TestPrune duplicate `QueryAffectedTests`

### Current shape

Two `db.QueryAffectedTests` call sites:

1. **Per-FileChecked** (`TestPrunePlugin.fs:1080–1085`): every `FileChecked`
   event with new changed symbols runs `db.QueryAffectedTests(distinct)`.
   Result is stored in `state.AffectedTests`.
2. **In `flushAndQueryAffected`** (`TestPrunePlugin.fs:715–723`): on
   `BuildCompleted`, flush pending analysis to DB, then run
   `db.QueryAffectedTests(symbols)`. Result overwrites
   `state.AffectedTests`.

### What does the per-FileChecked query produce that BuildCompleted doesn't?

A *speculative* `AffectedTests` list, computed before pending analysis is
flushed to the DB. It can be wrong (it queries against pre-flush DB state),
but it's "good enough for now."

The CHANGELOG entry (`src/FsHotWatch.TestPrune/CHANGELOG.md:125–127`)
documents the rationale: "the `affected-tests` command now updates on every
`FileChecked` event … re-queries `QueryAffectedTests` against the
currently-persisted DB state without waiting for `BuildCompleted`."

### Who consumes it before BuildCompleted?

The `affected-tests` IPC command (`:827–841`). It reads
`state.AffectedTests`. That is the only consumer of the per-FileChecked
query's output that fires before BuildCompleted overwrites it.

`runTestsWithImpact` (`:756–759`) reads `state.AffectedTests` too, but only
after `flushAndQueryAffected` has just run — so it gets the BuildCompleted
query's value.

### Proposed change

Make `affected-tests` compute on demand from `state.ChangedSymbols`:

```fsharp
"affected-tests",
fun (state: TestPruneState) (_args: string array) ->
    async {
        let symbols = state.ChangedSymbols |> List.distinct
        let tests =
            if symbols.IsEmpty then []
            else db.QueryAffectedTests(symbols)
        let testsData = tests |> List.map (fun t -> {| ... |})
        return JsonSerializer.Serialize(testsData)
    }
```

Then drop `:1074–1085` entirely; the FileChecked handler still updates
`state.ChangedSymbols`, just not `state.AffectedTests`. Flip
`AffectedTests` to be set only by `flushAndQueryAffected`. The
`Volatile.Write(&changedSymbolsRef, ...)` cache-key snapshot stays.

This trades:
- one SQL query per FileChecked-with-new-symbols (today, eager) → one SQL
  query per `affected-tests` IPC call (proposed, lazy).
- the IPC call gets a fresh answer rather than a snapshot taken at the
  last FileChecked.

Under rapid-save storms with no IPC clients, that's a strict reduction. With
an IPC client polling once per second it's roughly even.

**Survey claim correction:** the survey said "the BuildCompleted query is
authoritative; drop the per-FileChecked query." The `flushAndQueryAffected`
query *is* authoritative for the test run, but the per-FileChecked query
exists to serve `affected-tests` between builds. They're not redundant —
they're serving different consumers. The cleanup is to recognize that the
between-builds consumer can compute on demand.

### Phase 3 coupling

Phase 3 (TestPrune migration to RunExclusive) restructures the Update
handler — the FileChecked branch (`:976–1110`) is the most likely to be
rewritten. Three options:

1. **Land Item 8 before Phase 3** — small isolated diff (~30 lines), proves
   the IPC-on-demand pattern, reduces the surface area Phase 3 has to
   migrate. **Recommended.**
2. **Land it during Phase 3** — fold it into the migration commit. Risk: the
   migration commit grows; harder to bisect.
3. **Land it after Phase 3** — wait for the dust to settle. Risk: Phase 3
   inherits the speculative-query pattern and may bake it deeper.

Option 1 is the lowest-coupling path. The `state.ChangedSymbols` and
`state.AffectedTests` fields aren't on Phase 3's restructuring critical
path; whatever the Update handler shape becomes, the IPC handler shape is
independent.

### Risk

Low–Medium. The behavior change is observable: an `affected-tests` IPC
client that today gets a stale (pre-flush) answer will now get a fresh
answer (post-write to the DB but pre-flush of the latest pending analysis).
The freshness is strictly better, but if any tooling has a workaround for
the stale-snapshot quirk, it'd see different results.

### Cost

Low. ~30 lines deleted, ~10 added.

### TDD strategy

- New test: `affected-tests` IPC returns a query computed from
  `state.ChangedSymbols` without requiring a BuildCompleted.
- New test: `affected-tests` IPC returns `[]` when `ChangedSymbols` is
  empty, without hitting SQLite (use a counting fake `ISymbolStore`).
- Update existing `affected-tests` tests that depended on the eager
  population pattern: they become slightly different in setup but not in
  observable behavior.

## Out-of-scope notes

- **Watcher → typed paths at the watcher boundary.** Item 6 stops at
  `FileCheckResult`. The complementary cleanup — `EmitFileChanged` carrying
  `AbsFilePath list` instead of `string list` — would normalize the *other*
  source of paths in the system. Worth a separate follow-up. Risk: macOS
  FSEvents emits paths in a system-canonical form that's already normalized
  via `Path.GetFullPath` to the same value, so this is purely cosmetic
  unless someone is symlinking the repo.
- **`hasFile` returns `None` vs. raising.** Site 5A: under heavy contention
  it's possible that `File.Exists` races with `File.GetLastWriteTimeUtc`.
  The proposed code handles this by re-raising — that's the honest signal.
  Build will fail loudly; merkle won't be poisoned. If we observe this
  becoming a real flake source in practice, consider adding *one* retry
  inside `hashFile` with a 50ms backoff. Not adding speculatively.
- **TestPrune's `try/with ex ->` around `flushAndQueryAffected`** at
  `:1138–1141` and `:1265–1271` is not in this item set. Those are
  legitimate: SQLite schema-drift recovery is a real consumer of the catch.
  No change recommended.
