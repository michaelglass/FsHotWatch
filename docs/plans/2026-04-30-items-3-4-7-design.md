## Item 3 — File-change dedup layers

### What the survey claimed

Three (or four) overlapping dedup layers:

1. `Watcher.fs` SHA-256 hash + unbounded `ConcurrentDictionary<string, byte[]>`
2. `Daemon.fs` debounce + `List.distinct` per batch
3. `CheckPipeline.fs:151–172` `CancelPreviousCheck` per-file CTS
4. FCS task cache (per-file content hash)

Survey assertion: the change-agent MailboxProcessor already serializes batches
and within-batch `List.distinct` dedupes, so the per-file CTS guards a race
that may not actually occur.

### What the code actually does (citing file:line)

**Layer 1 (Watcher hash) is misnamed.** The `fileHashes` dictionary lives in
`src/FsHotWatch/Watcher.fs:10` and `hasContentChanged` is defined at
`Watcher.fs:14`, but the FileSystemWatcher / FSEvents callback path
(`Watcher.fs:133–195`) **never calls it**. The only callers are
`Daemon.fs:447` and `Daemon.fs:458`, both inside `processBatch`. So this is
not a per-event filter at the watcher boundary; it is a content-vs-mtime
filter applied once per batch, after debounce. The function lives in
`Watcher.fs` for organizational reasons only. The "three layers" framing was
incorrect — it's one layer, doing one job (mtime-only event suppression for
format-on-save round-trips that produce no content delta).

**Layer 2 (debounce + List.distinct) does dedupe within a batch.**
`Daemon.fs:1087–1133` runs a single `MailboxProcessor` (`changeAgent`) that
debounces and calls `processBatch` strictly serially. Within `processBatch`,
`sourceFiles |> List.distinct` (`Daemon.fs:433`) and `projFiles |> List.distinct`
(`Daemon.fs:456`) collapse repeated paths from the debounce window.

**Layer 3 (per-file CTS) is load-bearing — survey was wrong.** The
`scanMailbox` (`Daemon.fs:1147–1178`) is a *separate* MailboxProcessor from
`changeAgent`. They run concurrently. `performScan` calls
`pipeline.CheckFile(...)` (`Daemon.fs:952, 955`) at the same time
`processBatch` may be running its own `pipeline.CheckFile(...)` calls
(`Daemon.fs:547, 550, 561`). When a file changes mid-scan, two checks can be
in flight against the same path. The CheckCache is keyed by content hash
(`CheckPipeline.fs:68–75`), so the *cached values* do not collide, but
`host.EmitFileChecked` is invoked once per completed check
(`Daemon.fs:527`). Without `CancelPreviousCheck` (`CheckPipeline.fs:154`), a
slow scan-side check could emit a stale `FileChecked` *after* the batch-side
check already emitted the fresh one — plugins (FCS error ledger, lint,
analyzers) would observe newer-then-older event ordering and re-publish
stale errors. The CTS guards exactly this scan-vs-batch race.

**Layer 4 (FCS task cache) is content-hash dedup, not ordering.** Independent
purpose: skip recompute when a path returns to a content already seen.

### Proposed change

Keep `CancelPreviousCheck`. **Do not delete it** — the survey's premise was
wrong.

Two smaller cleanups remain:

1. **Move `hasContentChanged` + `fileHashes` out of `Watcher.fs`.** It has
   nothing to do with the watcher; rename it `ContentDedup.fs` or fold it
   into a private helper inside `Daemon.fs`. The `ConcurrentDictionary` is
   "unbounded" only in the sense that fsproj-tracked files are; it never
   exceeds the registered file count and trims on delete (`Watcher.fs:17`).
   No size leak.

2. **Document the scan-vs-batch race** in a comment above
   `CancelPreviousCheck`. Right now the only hint is `Cancels any previous
   in-flight check` (`CheckPipeline.fs:151`). A future reader may delete it
   for the same reason the survey suggested deleting it.

### Risk

Low. Both changes are documentation/refactoring.

### TDD strategy

A regression test demonstrating the scan-vs-batch race would be valuable. Two
deterministic options:

- Stub `pipeline.CheckFile` to introduce a programmable delay; trigger a scan,
  midway issue a `processBatch` for the same file with new content; observe
  that the emitted `FileChecked` carries the *newer* `Version`
  (`CheckPipeline.fs:77`, `FileCheckResult.Version`).
- Or, in a daemon-level integration test, run scan + concurrent file mutation
  with the CTS deleted in a branch, and confirm the test fails.

These tests should land *before* anyone tries to delete `CancelPreviousCheck`.

## Item 4 — `ScanAgent` volatile + bootstrap ref

### What the survey claimed

`ScanAgent` (now `Daemon.fs:359–381`) wraps a MailboxProcessor with
`Volatile.Read/Write` mutable fields plus a separate `ScanSignal` agent. The
`scanAgentRef = ref None` bootstrap (`Daemon.fs:1145`) exists so the agent
loop can write into a wrapper that doesn't yet exist at start time. Possibly
cargo-culted from the CLAUDE.md plugin-state rule.

### What the code actually does

`ScanAgent` (`Daemon.fs:359–367`):

```fsharp
type ScanAgent =
    private
        { Agent: MailboxProcessor<ScanMsg>
          mutable CurrentState: ScanState
          mutable CurrentGeneration: int64 }

    member this.GetScanState() = Volatile.Read(&this.CurrentState)
    member this.GetGeneration() = Volatile.Read(&this.CurrentGeneration)
```

Read sites:

- `Daemon.fs:753` `GetScanState()` → exposed via `Daemon.GetScanState`, called
  from tests and `FormatScanStatus` (`Daemon.fs:805`).
- `Daemon.fs:756` `GetScanGeneration()` → exposed via `Daemon.GetScanGeneration`,
  called by IPC config (`Daemon.fs:848`) and `WaitForScanGeneration`
  (`Daemon.fs:852`).
- `Daemon.fs:759` `SetScanState` → only from internal test helpers.

Write sites:

- `Daemon.fs:1161–1162` inside the scan-agent loop, after `performScan`
  completes.
- `Daemon.fs:381` `setScanStatus` (test-only).

The reads run on the IPC server thread (different from the scan-agent's
synchronization context); the writes run on the scan-agent's loop. **The
`Volatile.Read/Write` calls are load-bearing for x86/ARM memory ordering** —
not cargo-culted. CLAUDE.md's "all mutable plugin state uses Volatile" rule
applies to plugin handlers, but the same correctness concern applies here.

The bootstrap `scanAgentRef = ref None` (`Daemon.fs:1145`) exists because the
agent's body needs a handle to the wrapper to call `Volatile.Write` on its
fields, but the wrapper holds the agent. Classic cycle.

### What's actually wrong

The wrapper is the wrong abstraction. Two cleaner shapes:

**Option A — Single agent, reads via `PostAndReply`.**

Drop the wrapper entirely. State lives in the agent's recursive loop. Reads
are mailbox round-trips. Sub-microsecond reply is negligible for the cold-path
callers (IPC + `FormatScanStatus`).

```fsharp
type private ScanMsg =
    | RequestScan of CancellationToken * AsyncReplyChannel<unit>
    | GetState of AsyncReplyChannel<ScanState>
    | GetGeneration of AsyncReplyChannel<int64>
```

Replaces three operations (`GetScanState`, `GetGeneration`, `SetScanState`)
with three message variants. Eliminates `Volatile.Read/Write`, `mutable`
fields, and the `scanAgentRef` cycle.

**Option B — Expose state as snapshot via the agent's existing reply.**

Have `RequestScan` reply with the post-scan state and have callers cache the
last reply. More invasive (every reader becomes async); not worth it.

**Recommend Option A.** It strictly removes complexity.

### PluginHost lock-then-publish-outside-lock

`PluginHost.fs:29–54` uses `lock statusLock` for the status-map mutation and
fires `statusChanged.Trigger(name, status)` outside the lock. Comment at
`PluginHost.fs:20–23` documents the reason: subscribers may call
`GetAllStatuses()` re-entrantly, so the trigger must not hold the lock.

This is a different pattern. It's correct for what it does, but it's a
shared-mutable-map-with-event abstraction that arguably *should* be a
mailbox-with-broadcast (matching the proposed `ScanAgent` shape). It is not,
however, urgent: there's no observed bug, and migration would touch
`statusChanged` subscribers across the codebase.

**Recommendation: out of scope for items 3/4/7.** File a follow-up for a
unified "agent-owned observable state" abstraction once the `ScanAgent`
migration validates the pattern.

### Risk

Low–Medium. The agent migration is mechanical. Risk: any caller that today
reads `GetScanState()` synchronously inside another lock or async context
must not deadlock. Quick audit: `FormatScanStatus` (no locks),
`GetScanGeneration` (no locks), test helpers (no locks). Safe.

### TDD strategy

Existing daemon tests around scan generation (`tests/FsHotWatch.Tests/DaemonTests.fs`)
and `WaitForScanGeneration` exercise the read path; they will catch
behavioral regressions. Add one new unit test:

- After triggering a scan, `GetScanState()` returns `ScanComplete _` (not
  stale `ScanIdle`). Today this is happenstance ordering of `Volatile.Write`
  before `reply.Reply`; in the migrated code it becomes inherent (state lives
  in the next `loop` iteration).

## Item 7 — `SolutionChanged` asymmetry

### What the survey claimed

`solutionFile: string option ref` collapses multiple `SolutionChanged` events
to last-one-wins, while `projFiles: string list` accumulates. The asymmetry
buys nothing because both paths emit identical `EmitFileChanged` calls.

### What the code actually does

`Daemon.fs:410–416`:

```fsharp
let mutable sourceFiles = []
let mutable projFiles = []
let mutable solutionFile = None

for c in changes do
    match c with
    | SourceChanged files -> sourceFiles <- files @ sourceFiles
    | ProjectChanged files -> projFiles <- files @ projFiles
    | SolutionChanged f -> solutionFile <- Some f
```

`Daemon.fs:466`: `ctx.Host.EmitFileChanged(SolutionChanged solutionFile.Value)`

Plugin consumers of `SolutionChanged`:

- `src/FsHotWatch.FileCommand/FileCommandPlugin.fs:300` — `| SolutionChanged _ -> []`
- All other plugins match on `SourceChanged` only or fall through.

**No subscriber reads the path payload.** Confirmed via
`grep -rn 'SolutionChanged' --include='*.fs' src/`. The path is dead data.

The downstream effect of a `SolutionChanged` is solely the rediscovery branch
at `Daemon.fs:468–488`, gated on `hasSolution || not projFilesChanged.IsEmpty`.
The path is never inspected.

### Proposed change

Make `SolutionChanged` payload-less. Smallest correct change:

```fsharp
// Events.fs
type FileChangeKind =
    | SourceChanged of files: string list
    | ProjectChanged of files: string list
    | SolutionChanged   // was: of file: string
```

Update three call sites:

- `Watcher.fs:114` → `SolutionChanged`
- `Daemon.fs:416` → drop the binding (`solutionFile`) and replace with a
  simple `mutable hasSolution = false`. Set it `true` on `SolutionChanged`.
- `Daemon.fs:466` → `ctx.Host.EmitFileChanged(SolutionChanged)`
- `FileCommandPlugin.fs:300` → unchanged (already wildcard).
- All test sites that construct `SolutionChanged "foo.sln"` drop the arg.

The alternative — make solutions a `string list` matching projects — adds a
field nobody reads. Reject.

### Risk

Low. The event ABI changes, but this is an internal type (no IPC wire format
involves the discriminator's payload). Public API surface: `Events.fs` is
exported; consumers of the `FsHotWatch` core library could in principle match
on `SolutionChanged f`. Per CLAUDE.md, version bumps are automated by
`fssemantictagger`; the API change will be picked up. Acceptable for a minor
bump in this pre-1.0 framework.

### TDD strategy

- Update existing tests at `WatcherTests.fs:86–91`, `EventTests.fs:12`,
  `DaemonTests.fs:351`, `BuildPluginTests.fs:301`, `FormatCheckPluginTests.fs:66`,
  `FileCommandPluginTests.fs:209`. All currently construct
  `SolutionChanged "test.sln"`; update to `SolutionChanged`.
- No new behavioral test needed: the change is purely a payload removal.

## Suggested ordering

Item 7 and item 4 both touch `Daemon.fs` but in different regions
(`processBatch` vs. agent construction). They are independent and can land in
either order or together. Item 3's small cleanups (move `hasContentChanged`,
add a comment, optional regression test) are independent of both.

Recommended sequence:

1. **Item 7** first. Smallest diff, lowest risk, immediate readability win.
   Lands one commit.
2. **Item 4** next. Migrate `ScanAgent` to a single-agent shape with
   `PostAndReply` reads. Lands one commit (perhaps two if test additions are
   sizeable).
3. **Item 3** last, as a doc-only PR. Move `hasContentChanged`, add the
   comment above `CancelPreviousCheck` explaining the scan-vs-batch race.
   Optionally add a regression test for the race.

Each is a single jj commit (per CLAUDE.md push-direct-to-main).

## Out-of-scope notes

Things noticed but not part of items 3/4/7:

- `PluginHost.fs:24–54` lock-then-publish-outside-lock is a sibling pattern
  to `ScanAgent`'s volatile fields. Both could collapse to "agent-owned
  observable state." Worth a Phase 5 follow-up after item 4 validates the
  pattern.
- `Daemon.fs:865` `tcs` is a `TaskCompletionSource<unit>` set inside a
  `cts.Token.Register` callback. The `_reg` is `use`-bound, so dispose runs
  on async-block exit. Looks correct, but inverted control flow — a small
  helper `Async.untilCancelled cts` would read better.
- `processBatch` (`Daemon.fs:406–569`) is 160 lines. Splitting the
  re-discover branch and the file-check branch into named helpers would help
  the next reader.

None of these are bugs. They're stylistic follow-ups.
